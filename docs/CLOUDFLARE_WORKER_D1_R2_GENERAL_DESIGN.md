# General Cloudflare Worker + D1 + R2 Integration Design

This document generalizes the Cloudflare sync implementation used by Cairn
into a reusable design for any application that needs authenticated APIs,
structured metadata, and durable file storage.

## 1. Design objective

Use one Cloudflare Worker as the only public application boundary:

```text
Web / desktop / mobile client
          |
          | HTTPS API
          v
Cloudflare Worker
   |              |
   | D1           | R2
   v              v
metadata       binary objects
```

The responsibilities are deliberately separated:

- Worker: routing, authentication, authorization, validation, version checks,
  upload orchestration, and response shaping.
- D1: users, tenants, records, object metadata, versions, status, and indexes.
- R2: large or binary files such as images, documents, exports, and media.
- Client: local cache, upload progress, retry UI, and explicit conflict decisions.

Do not store large file bodies in D1. Do not let clients access D1 or R2
credentials directly.

## 2. When this architecture fits

This design fits applications with:

- JSON metadata and relational queries;
- user-owned or tenant-owned files;
- browser, desktop, or mobile clients;
- asynchronous or resumable uploads;
- a small-to-medium API surface;
- a need for edge deployment without maintaining an origin server.

It is not automatically the right choice for high-volume analytics, complex
cross-region transactions, large server-side joins, or workloads that require a
traditional long-running process. Those cases may need an external database,
queue, or object-processing service in addition to Workers.

## 3. Core invariants

Establish these before writing routes:

1. Every request is authenticated before reading or mutating private data.
2. Every record and object key is scoped by tenant or user identity.
3. D1 metadata is the source of truth for object ownership and availability.
4. R2 keys are generated by the server from validated identifiers; clients do
   not choose arbitrary bucket prefixes.
5. A successful metadata commit must not claim that an object exists until the
   object has been uploaded and verified.
6. Mutations carry a version or idempotency token so retries do not corrupt
   state.
7. A failed cloud operation does not destroy the client's local copy.
8. Secrets never appear in source, Wrangler configuration, logs, URLs, or
   returned JSON.
9. Large bodies are bounded before parsing or buffering.
10. Every external error has a stable machine-readable code and a safe message.

## 4. Resource model

### 4.1 D1 stores metadata

A generic schema can start with these tables:

```sql
CREATE TABLE users (
  id TEXT PRIMARY KEY,
  email TEXT NOT NULL UNIQUE,
  password_hash TEXT,
  status TEXT NOT NULL DEFAULT 'active',
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE records (
  id TEXT PRIMARY KEY,
  owner_id TEXT NOT NULL,
  title TEXT NOT NULL,
  version INTEGER NOT NULL DEFAULT 1,
  status TEXT NOT NULL DEFAULT 'active',
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  deleted_at TEXT,
  FOREIGN KEY (owner_id) REFERENCES users(id)
);

CREATE TABLE objects (
  id TEXT PRIMARY KEY,
  owner_id TEXT NOT NULL,
  record_id TEXT NOT NULL,
  object_key TEXT NOT NULL UNIQUE,
  content_type TEXT NOT NULL,
  byte_size INTEGER NOT NULL,
  content_hash TEXT NOT NULL,
  object_version INTEGER NOT NULL,
  status TEXT NOT NULL DEFAULT 'pending',
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  FOREIGN KEY (owner_id) REFERENCES users(id),
  FOREIGN KEY (record_id) REFERENCES records(id)
);

CREATE INDEX records_owner_updated ON records(owner_id, updated_at DESC);
CREATE INDEX objects_record_path ON objects(record_id, object_key);
CREATE INDEX objects_owner_status ON objects(owner_id, status);
```

For multi-tenant systems, use `tenant_id` on every private table and include
it in every unique constraint and index. A user ID alone is not a sufficient
tenant boundary when organizations, teams, or shared folders exist.

### 4.2 R2 stores objects

Use a deterministic, server-generated key:

```text
tenants/{tenantId}/records/{recordId}/objects/{safeRelativePath}
```

Never concatenate an unchecked client path. Reject absolute paths, backslashes,
empty segments, `.` and `..`, control characters, and unexpected extensions.

Keep the R2 key in D1 so the Worker can authorize access before calling R2.
The client should receive a logical object ID or a short-lived download URL,
not an unrestricted bucket listing.

## 5. Worker project layout

```text
apps/api-worker/
  src/
    index.ts              # fetch entry point and route dispatch
    env.ts                # typed bindings and secret names
    auth/
      password.ts
      session.ts
      routes.ts
    records/
      routes.ts
      repository.ts
      validation.ts
    objects/
      routes.ts
      keys.ts
      validation.ts
    shared/
      errors.ts
      json.ts
      ids.ts
  migrations/
    0001_initial.sql
    0002_add_object_status.sql
  wrangler.jsonc
  README.md
```

Keep route handlers thin. Put SQL in repositories, input checks in validation
modules, and object-key rules in one shared module. This prevents the same
authorization or path rule from being copied inconsistently across routes.

## 6. Wrangler configuration

```jsonc
{
  "$schema": "node_modules/wrangler/config-schema.json",
  "name": "example-api-worker",
  "main": "src/index.ts",
  "compatibility_date": "2025-01-01",
  "d1_databases": [
    {
      "binding": "DB",
      "database_name": "example-db",
      "database_id": "<D1 UUID>",
      "migrations_dir": "migrations"
    }
  ],
  "r2_buckets": [
    {
      "binding": "FILES",
      "bucket_name": "example-files"
    }
  ]
}
```

Only non-secret resource identifiers belong in this file. Passwords, signing
keys, API tokens, and initialization secrets belong in Worker Secrets or an
environment-specific secret store.

Cloudflare records applied migrations in the D1 migrations table. Use named
migrations and apply local and remote databases separately; do not treat a
successful Worker deployment as proof that the remote schema is current. See
the [D1 migrations documentation](https://developers.cloudflare.com/d1/reference/migrations/).

## 7. Authentication and authorization

### 7.1 Recommended session flow

For a private application:

1. `POST /api/auth/init` creates the first administrator exactly once.
2. `POST /api/auth/login` verifies the password and creates a random session
   token.
3. Store only a hash or digest of the session token in D1.
4. Return the token in a Secure, HttpOnly, SameSite cookie for browser clients.
5. For desktop clients that cannot use cookies reliably, use a short-lived
   bearer token stored in the OS-protected application data directory.
6. `POST /api/auth/logout` revokes the session server-side.

Do not implement password reset by re-running the initialization endpoint. Add a
separate, authenticated recovery flow before exposing that capability.

### 7.2 Authorization rule

Every private query must include the authenticated owner or tenant in SQL:

```sql
SELECT id, title, version
FROM records
WHERE id = ? AND tenant_id = ? AND deleted_at IS NULL;
```

Do not fetch by ID first and authorize in a later branch. The scoped query is the
authorization boundary and prevents accidental cross-tenant reads.

## 8. API contract

Start with a small, explicit contract:

```text
GET    /api/health
POST   /api/auth/init
POST   /api/auth/login
POST   /api/auth/logout
GET    /api/records
GET    /api/records/:recordId
PUT    /api/records/:recordId/manifest
DELETE /api/records/:recordId
PUT    /api/records/:recordId/objects/:path
GET    /api/records/:recordId/objects/:path
DELETE /api/records/:recordId/objects/:path
```

Every JSON error should have the same shape:

```json
{
  "code": "invalid_object_metadata",
  "message": "Object metadata is invalid.",
  "details": { "field": "contentHash" }
}
```

Use stable codes for client behavior and human-readable messages for logs and
support. Do not return stack traces, SQL, tokens, or password details.

## 9. Upload design

### 9.1 Small or trusted-client uploads: Worker proxy

The client sends the object to the Worker. The Worker:

1. authenticates and authorizes the record;
2. checks path, content type, declared size, and maximum size;
3. reads the body with a hard limit;
4. computes or verifies SHA-256;
5. writes to R2;
6. upserts the object row in D1;
7. returns the object receipt.

This is the simplest pattern and is suitable for small files or desktop clients
where the Worker should own all validation.

### 9.2 Large browser uploads: presigned URL

For large uploads, use a two-phase protocol:

```text
Client -> Worker: request upload URL and object ID
Worker -> Client: short-lived signed PUT URL
Client -> R2: upload bytes directly
Client -> Worker: complete upload with hash and size
Worker -> R2: HEAD object and verify metadata
Worker -> D1: commit object row as ready
```

R2 presigned URLs are bearer tokens, so keep their lifetime short, bind the
content type where possible, and never expose broad bucket credentials. R2
Workers bindings do not themselves generate presigned URLs; signing requires an
S3-compatible client or signing library. See the [official R2 presigned URL
documentation](https://developers.cloudflare.com/r2/api/s3/presigned-urls/).

### 9.3 Never commit metadata before the object exists

Use `pending` and `ready` states for two-phase uploads. A cleanup job can remove
pending rows and orphaned R2 objects after a retention window.

## 10. Manifest and synchronization protocol

For a collection of files, send metadata separately from bytes:

```json
{
  "recordId": "record-123",
  "title": "Example",
  "version": 1,
  "baseVersion": 3,
  "objects": [
    {
      "path": "path.json",
      "contentType": "application/json",
      "byteSize": 2048,
      "contentHash": "<64 lowercase hex characters>"
    }
  ]
}
```

The manifest must never contain the object bytes. In the Cairn incident, a
structural TypeScript subtype carried a runtime `bytes` property into the
manifest JSON and exceeded the Worker limit. Build metadata objects explicitly
instead of spreading file objects with extra runtime fields.

Use optimistic concurrency:

1. Client reads the cloud manifest and its version.
2. Client compares local and remote metadata.
3. If identical, finish without transfer.
4. If only local exists, upload with `baseVersion: 0`.
5. If only cloud exists, download and install atomically.
6. If both differ, return `409 stale_version` or a conflict result.
7. The UI asks whether to overwrite; only explicit confirmation retries with
   the remote version as `baseVersion`.

Never silently overwrite a newer remote version. A retry after a timeout must be
safe and idempotent: same hash and same version should be treated as success.

## 11. Download and install design

The Worker must authorize every object download against D1 before calling R2.
The client should:

1. fetch the manifest;
2. download only allowlisted objects;
3. verify byte size and SHA-256 locally;
4. stage files in a temporary directory;
5. atomically install the complete record;
6. update the local last-synced timestamp only after installation succeeds.

Do not replace a usable local record with a partial download. If one object
fails validation, keep the old local record and surface a retryable error.

## 12. Security checklist

- HTTPS in production; reject credentials embedded in URLs.
- Passwords hashed with a slow, salted password KDF; never encrypt or log raw
  passwords.
- Session tokens random, short-lived, revocable, and stored only as digests.
- SameSite and CSRF protection for cookie-authenticated browser mutations.
- CORS allowlist, not `*`, when credentials are involved.
- Rate-limit login, initialization, upload URL creation, and destructive routes.
- Validate IDs and object paths before SQL or R2 key construction.
- Enforce per-object and per-manifest byte limits.
- Verify content type, declared size, and content hash.
- Use tenant-scoped SQL for every private operation.
- Do not return D1 or R2 credentials to clients.
- Treat presigned URLs as bearer tokens and expire them quickly.
- Keep secrets out of `wrangler.jsonc`, `.env` committed files, logs, and URLs.

## 13. Deployment lifecycle

### One-time setup

```bash
bunx wrangler login
bunx wrangler d1 create example-db
bunx wrangler r2 bucket create example-files
```

Put the returned D1 UUID and bucket name in `wrangler.jsonc`, then create
secrets:

```bash
bunx wrangler secret put ADMIN_INIT_SECRET \
  --config apps/api-worker/wrangler.jsonc
```

### Every schema or Worker release

```bash
bun run test
bun run typecheck
bunx wrangler d1 migrations apply example-db --remote \
  --config apps/api-worker/wrangler.jsonc
bunx wrangler deploy \
  --config apps/api-worker/wrangler.jsonc
curl -fsS https://example-api-worker.example.workers.dev/api/health
```

Deploy the Worker and apply migrations from the same commit. Keep staging and
production bindings separate. Never use the local D1 database as evidence that
the remote D1 schema is ready.

## 14. Testing strategy

### Pure tests

- ID and object-path validation;
- content type mapping;
- manifest size and byte exclusion;
- hash verification;
- version comparison and idempotency;
- authorization query construction;
- error-code mapping.

### Worker route tests

- unauthenticated requests return 401;
- another tenant cannot read or mutate a record;
- malformed JSON and oversized bodies return field-level errors;
- invalid content type, size, hash, and path are rejected;
- manifest PUT is atomic from the client's perspective;
- stale versions return 409 with the current cloud version;
- R2 failures do not create a ready D1 object row;
- delete removes or tombstones metadata and cleans R2 objects.

### Client tests

- local-only upload;
- cloud-only download;
- identical manifests are a no-op;
- conflicting manifests require confirmation;
- progress reports book and object counts;
- closing a status Toast does not alter sync state;
- a new progress snapshot reopens the Toast;
- failed transfers preserve local playback.

## 15. Observability and operations

Return a request ID from the Worker and include it in structured logs. Log only:

- route and method;
- status and stable error code;
- tenant/user pseudonymous ID;
- record ID;
- byte counts and duration;
- request ID.

Do not log passwords, bearer tokens, cookies, object contents, or full signed
URLs. Monitor login failures, 4xx validation rates, 409 conflicts, 5xx rates,
R2 object failures, pending upload age, and D1 query latency.

## 16. Cairn mapping

The current Cairn implementation follows this design as follows:

| General concept | Cairn implementation |
| --- | --- |
| Worker API | `apps/sync-worker/src/index.ts` and `src/sync/routes.ts` |
| D1 metadata | books, resources, sessions, and progress migrations |
| R2 objects | allowlisted playback JSON and cover resources |
| Local manifest | `packages/core/src/sync/manifest.ts` |
| Local bundle export | `packages/core/src/sync/local.ts` |
| Conflict handling | explicit per-book overwrite confirmation |
| Progress UI | `SyncProgress` and dismissible shelf Toast |
| Privacy boundary | chapters, cache, traces, chat, and MP3 remain local |

The most important reusable lesson is to make the sync boundary explicit:
metadata, object bytes, private source text, and derived cache data should not be
mixed into one upload payload or one storage layer.

## 17. Definition of done

A project is ready for production use when:

- the Worker health endpoint passes;
- remote migrations are applied and listed;
- D1 and R2 bindings are verified against the intended environment;
- initialization and login are tested without exposing secrets;
- every private route has an authorization test;
- object uploads verify content type, size, and hash;
- retries are idempotent and stale versions are explicit;
- local or client-side data remains usable after network failure;
- deployment and rollback commands are documented;
- logs and error responses contain no credentials or file contents.
